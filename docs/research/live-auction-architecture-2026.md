# Live Auction architecture: hosting and runtime options

Research date: 2026-10-05. This note supersedes the provider-fact section of [Live Auction reliability on the free tier](live-auction-free-tier-2026.md). That note could not see the deployed revision, regions, timings, or production logs. This one can, so it is written against measured production numbers. Everything below is checked against the repository in this checkout plus primary provider documentation. Where a number could not be verified from the page that owns it, the note says so instead of guessing.

## Executive summary

This is a **shape mismatch, not a scale problem**. One Auction moves a few hundred rows and produces a snapshot measured at ~67 KiB, yet a single `SELECT ... FOR UPDATE` on one `auction` row produced 644 command calls with a mean lock wait of 1,934 ms and a maximum of 10,669 ms. The database is idle for more than 99% of the auction's wall clock. The latency is self-inflicted by four things, all of which are visible in this repository:

1. **Every command talks to Postgres ~22 times while holding the row lock.** `lockLiveAuction` takes the lock in `live-command.ts`, then `place-bid.ts` performs ~22 awaited `client.query(...)` round trips before `commit`. The lock is held for the whole conversation, not for the ~0.04–20 ms of server-side work per statement.
2. **The protocol is duplicated at the edges.** 301 `finalize` commands for 39 Player Presentations (7.7×) because each of the 11 browsers wakes the close, and 90 of 192 bids (47%) are rejected `stale_revision` — each rejection still being a full lock-holding transaction that inserts a `bid_attempt` row, a command row, and commits.
3. **The broadcast path is a 67 KiB snapshot per client per revision.** Supabase Broadcast carries only `{revision:N}`, so each of the other 10 clients re-pulls the whole snapshot, which triplicates the same facts (`players[]` + `openSales[]` + `teams[].players[]`) and re-runs four duplicated queries.
4. **The connection model is misconfigured, not overloaded.** `DATABASE_URL` points at the Supavisor **session-mode** pooler (port 5432) while `getPool()` is `new Pool({ connectionString })` with **no `max`** — node-postgres defaults to 10 clients per pool ([pg.Pool](https://node-postgres.com/apis/pool)) — and Vercel runs many concurrent Function instances. The session pooler's backend pool is `pool_size: 15` on this project, which is exactly what the ~4,900 `(EMAXCONNSESSION) max clients reached in session mode - max clients are limited to pool_size: 15` errors say.

**Recommendation: keep Vercel + Supabase, and fix the execution model.** Phase 1 is configuration and protocol (transaction pooler :6543, explicit `max`, one finalizer, deltas instead of snapshots). Phase 2 moves each command into one PostgreSQL function so a command is **one** round trip instead of ~22. Do not re-platform to a container or to a per-auction actor until the beta runs more than one concurrent Live Auction — a threshold ADR 0005 already forbids on the free tier. Options 3, 4 and 5 become the right answers at 10–50 concurrent auctions, and this note gives the trigger conditions and the break-glass costs.

### The arithmetic that decides the question

- Arrival rate: 644 ÷ 7,200 s = **0.09 commands/s**. A resource that serves one command at a time at 0.09 commands/s has a utilisation of well under 1%.
- Total lock wait: 644 × 1,934 ms = **1,245,496 ms ≈ 1,245 s ≈ 20.8 minutes**, or **17% of the auction's wall clock spent queueing on a row lock**.
- Statement work available to explain it: 644 × 22 = 14,168 statements; at the measured floor of 0.04 ms that is **0.6 s**; at the measured ceiling of 20 ms it is **283 s**. So real statement execution accounts for between **0.05% and 23%** of the observed lock wait. The remaining 77–99.95% is not CPU and not data: it is the lock being held across round trips, plus connection acquisition against a 15-backend session pooler, plus traffic that should never have been sent.
- Redundant traffic: removing the 262 surplus finalize transactions (301 − 39) and the 90 stale-revision bids removes **352 of 644 lock acquisitions ≈ 55%**, without changing a single rule.
- Volume headroom: a 67 KiB snapshot is **~0.014%** of the free plan's 500 MB database size ([Supabase pricing](https://supabase.com/pricing)). 11 concurrent Realtime connections use **5.5%** of the free plan's 200 concurrent peak connections ([Supabase Realtime limits](https://supabase.com/docs/guides/realtime/limits)).
- Derived egress estimate: if each of the other 10 clients re-pulls the 67 KiB snapshot on each committed revision, the auction moves at most 67 KiB × 10 × 644 = **≈421 MiB**, plus ~42 MiB for the caller's own post-command snapshot, so **≈0.45 GiB per auction**. Against Supabase Free's 5 GB egress that ceiling is **~11 auctions/month**; against Pro's 250 GB it is **~550 auctions/month** ([Supabase pricing](https://supabase.com/pricing)). This is an estimate derived from the given snapshot size and revision count, not a measurement.

## Options

### 1. Keep Vercel + Supabase, tuned

- **Change**: point `DATABASE_URL` at the **shared transaction pooler, port 6543**; set an explicit `max` on the pool (Supabase recommends **1 connection per serverless instance**, raising it only with evidence of queuing, and turning prepared statements off because transaction mode does not support them); set `connectionTimeoutMillis`; keep the pool at module scope ([Supabase connect guide](https://supabase.com/docs/guides/database/connecting-to-postgres)). Reduce round trips where the transaction is already clean. Collapse the snapshot: one authoritative shape, an ETag/revision keyed response, and deltas for the Bid feed and Roster. Stop every browser firing its own `finalize` — elect one waker, or move the wake into the database.
- **Bid latency expectation**: unchanged at zero contention (the critical section still contains ~22 round trips), but the queue drain is large. The measured mean is 1,934 ms; with connection queueing removed and ~55% of lock acquisitions deleted, the expectation is that the mean approaches the intra-region round-trip cost of the remaining transactions rather than the pooler queue. Treat that as an **estimate, not a measurement** — it needs a rehearsal to confirm. Max wait should drop sharply because the 10.7 s outlier is a queue-tail, and removing 7.7× finalize fan-out removes the burst.
- **At 11 clients on one auction**: fixes the errors. `(EMAXCONNSESSION)` disappears because the transaction pooler multiplexes many clients onto the 15 backends instead of pinning a session each. 11 clients × 1 connection per warm instance stays inside the free plan's 200 pooler clients ([compute and disk](https://supabase.com/docs/guides/platform/compute-and-disk)).
- **At 10–50 concurrent auctions**: 550 clients exceeds Free's **200** concurrent Realtime connections, and 50 × 0.45 GiB ≈ **22.5 GiB** in a two-hour window exceeds Free egress. Requires Supabase Pro: 500 concurrent connections included, then **$10 per 1,000**; 5M Realtime messages included, then **$2.50/M**; 250 GB egress then $0.09/GB ([Supabase pricing](https://supabase.com/pricing)). Note that per-auction lock contention does **not** get worse with more auctions — each Auction serialises on its own `auction` row — so the tuning that fixes one auction fixes 50 auctions' command path.
- **Connection-model fit with serverless**: this is the option that matches how Vercel actually behaves. Supabase's own guidance is the transaction pooler for Vercel Functions and a deliberately tiny application-side pool.
- **Dominant failure mode**: with `max: 1` per instance a single slow command queues every other command in the same instance. Also, transaction mode forbids session state, cursors, session advisory locks, `SET` and query pipelining, so any middleware that relies on those has to move inside the transaction ([transaction mode limitations](https://supabase.com/docs/guides/database/connecting-to-postgres)).
- **Migration effort**: `src/server/database/pool.ts` (pool options), `src/server/database/connection-string.ts` (leave as is — the SSL normalisation still applies), `src/server/auction-query/live-snapshot.ts` (shape and delta), `src/app/api/auctions/[id]/snapshot/route.ts`, `src/features/auctions/live/use-live-sync.ts` (deltas, single waker), `src/features/auctions/live/live-actions.ts` (finalize election). No change to `place-bid.ts`, `close-player.ts`, `live-command.ts`.
- **Monthly cost**: **$0** on the current free plan for one Auction; **$25** for Supabase Pro (first project, includes $10 compute credit = one Micro instance) when the beta needs more than one concurrent auction, plus **$0** on Vercel Hobby for a private non-commercial beta.
- **ADR verdict**: satisfies **0002** (Postgres still orders Bids), **0004** (Audit Entries unchanged), **0006** (still commit-before-acknowledge), **0007** (database deadlines and idempotent finalization are preserved; electing one waker makes the intent truer), **0008** (Supabase Realtime and brokered tokens unchanged), **0009** (one Auction Command module unchanged). Breaks nothing.

### 2. Move the command layer into Postgres (one RPC per command)

- **Change**: replace the ~22 round trips with a single `plpgsql` or SQL function per command — lock, authorise, validate, insert the `bid_attempt`/`sale`, bump the revision, write the outbox event, write the Audit Entry, store the command result, and return the outcome. The function can also carry the feasibility filter as one statement, or at least return the candidate rows in one reply so TypeScript stops driving the loop.
- **Bid latency expectation**: one application round trip + server execution + lock wait. At zero contention this is strictly shorter than the ~22-round-trip version; under contention it is dramatically better because the **lock is held for server execution only**, so the serialised critical section shrinks toward the measured 0.04–20 ms per statement rather than the network-bound duration of 22 await hops.
- **At 11 clients on one auction**: best available shape without new infrastructure. With 55% of lock acquisitions removed and the remaining transactions reduced to one round trip, the queue multiplier that produced the 10,669 ms tail largely disappears.
- **At 10–50 concurrent auctions**: scales linearly and cheaply, because the per-auction serialisation stays per-auction and each command is one connection checkout. The binding constraints become the ones listed for Option 1 (Realtime concurrent connections, egress, compute size), not the command path.
- **Connection-model fit with serverless**: excellent. One round trip per command is the ideal shape for a transaction pooler; the shorter critical section also means a `max: 1` pool per instance is less of a hazard.
- **Dominant failure mode**: **correctness risk from the port**, not availability. Legal Completion is the hard part: `src/server/auction-command/legal-completion-check.ts` loads a feasibility snapshot and then calls the shared engine in `src/domain/legal-completion.ts` and `src/domain/tiered-completion.ts` (the 200,000-node search). Those two engines are deliberately shared with Readiness so they "can never disagree". Porting them to SQL means maintaining one answer in two languages, or replacing the search with a single set-based feasibility statement. A secondary failure mode is that plpgsql is harder to unit-test from `src/**/*.test.ts`; the current unit and database test suites would need equivalents.
- **Migration effort**: **new** `supabase/migrations/*` functions (e.g. `place_bid`, `finalize_presentation`, `begin_manual_close`, `cancel_manual_close`, plus the corrections in `corrections.ts`); rewrite the bodies of `src/server/auction-command/place-bid.ts` and `close-player.ts` into thin `pool.query('select place_bid($1...)')` callers; a SQL or plpgsql counterpart of `legal-completion-check.ts`; keep `live-command.ts`'s types and `LiveCommandOutcome` as the contract so `live-actions.ts` and `use-live-sync.ts` do not move. `src/server/auction-query/live-snapshot.ts` can additionally become one function returning a single JSON document, which removes the ~20–24 query fan-out in one step.
- **Monthly cost**: **$0** beyond whatever Option 1 already requires. No new vendor.
- **ADR verdict**: satisfies **0002**, **0004**, **0006**, **0007**, **0008**. **0009** is arguably *more* satisfied than now: ADR 0009 says the Auction Command interface's "PostgreSQL implementation owns authorization, row locking, idempotency, rule validation, Audit Entries, revisions, and committed events", which is a description of this option. The one thing to watch is ADR 0009's "TypeScript may preview and explain Rules but cannot define a competing path": do not keep a second TS implementation of validation alongside the SQL one.

### 3. One long-lived container (Fly.io / Railway / Render / Hetzner-VPS)

- **Change**: run Next.js in a container in Singapore with a persistent `pg.Pool` (an application-side pooler is sufficient on its own for a static backend, per [Supabase pooling guidance](https://supabase.com/docs/guides/database/connecting-to-postgres/pooling-and-limits) and the [Supavisor FAQ](https://supabase.com/docs/guides/troubleshooting/supavisor-faq-YyP5tI)) connected by a **direct** connection rather than a pooler, optionally with an in-process WebSocket server replacing Supabase Broadcast.
- **Bid latency expectation**: best-case latency, because the pool is warm, there is no Supavisor hop, and no per-invocation checkout. The dominant term becomes Postgres execution plus in-region RTT. Note the constraint: Supabase direct connections are IPv6 unless the project has the IPv4 add-on, so a container needs IPv6 egress or the add-on ([connect guide](https://supabase.com/docs/guides/database/connecting-to-postgres)).
- **At 11 clients on one auction**: comfortable. One process, one pool, pooled connections amortised across all 11 clients; the ~1,245 s of lock wait drains because there is no pooler queue in front of it.
- **At 10–50 concurrent auctions**: the cleanest single-node answer. 550 clients on one process is fine; the ceiling becomes one node's capacity and the absence of failover. Horizontal scale reintroduces the shared-state problem unless you also move to Option 4 or keep Postgres as the only ordering authority.
- **Connection-model fit with serverless**: deliberately **not** serverless. That is the point — the current architecture's failure is the serverless/proxy interaction, and this option removes it.
- **Dominant failure mode**: you are now the operator. A single node is a single point of failure; deploys are not atomic like Vercel's; you own TLS, health checks, restarts, and log retention. If the in-process WebSocket replaces Supabase Broadcast, you also own a fan-out that must survive a restart mid-auction.
- **Migration effort**: add a Dockerfile and an adapter's custom server (or keep Vercel's build and run `next start` behind a reverse proxy); change `pool.ts` to a larger explicit `max` with `idleTimeoutMillis`; replace or bypass `src/server/realtime/notify-revision.ts` and `distributor.ts` if you add your own WebSocket, which then means replacing `use-live-sync.ts`'s Supabase channel with your own client. Everything in `auction-command/` stays as is.
- **Monthly cost** (Singapore, primary sources):
  - Fly.io `sin` is Singapore ([Fly regions](https://docs.fly.io/reference/regions/)): `shared-cpu-1x` 256 MB **$1.94/mo**, `shared-cpu-2x` 512 MB **$3.89/mo**, `performance-1x` 2 GB **$31/mo**, extra RAM **$5/GB/mo**, volumes **$0.15/GB/mo**, Asia-Pacific egress **$0.04/GB** ([Fly pricing](https://fly.io/pricing/)). Managed Postgres Basic is **$38/mo** — not needed if Supabase stays.
  - Railway: Southeast Asia Metal is **Singapore** (`asia-southeast1-eqsg3a`) ([Railway regions](https://docs.railway.com/deployments/regions)); Hobby is **$5/mo** including $5 of usage, RAM **$10/GB/mo**, CPU **$20/vCPU/mo**, egress **$0.05/GB** ([Railway plans](https://docs.railway.com/pricing/plans)).
  - Render: **Singapore** is a listed region ([Render regions](https://render.com/docs/regions)); Hobby workspace **$0** + compute, 512 MB/0.5 CPU **$7/mo**, 2 GB/1 CPU **$25/mo**, Render Postgres 1 GB **$19/mo**, and "WebSockets" is a listed feature ([Render pricing](https://render.com/pricing)).
  - Hetzner Cloud: Singapore (**SIN1**) is a location ([Hetzner Cloud](https://www.hetzner.com/cloud/)). **Prices not verified** — the product tables render the monthly and hourly figures client-side and did not appear in the fetched page, so no figure is quoted here.
- **ADR verdict**: satisfies **0002**, **0004**, **0006**, **0007** unchanged. It satisfies **0008** only if you keep Supabase Realtime; replacing it with your own socket **breaks ADR 0008** and needs a superseding ADR plus a replacement token broker (the current grant is a 120-second application HMAC, `grant.ts`). **0005** is broken by definition: it is no longer a zero-cost stack.

### 4. Per-auction single-writer actor (Cloudflare Durable Objects / PartyKit)

- **Shape**: one Durable Object per Auction holds 11 hibernatable WebSocket connections, serialises commands in-process, and appends to Postgres (or D1) as the durable log.
- **Bid latency expectation**: the lowest available. There is no row lock, no configuration change, and no pooler: the actor is the serialisation point and it is already warm. Where the current mean is 1,934 ms, a same-region actor answering from memory should be single-digit to low-tens of milliseconds plus persistence. Treat as an estimate.
- **At 11 clients on one auction**: this is the workload the primitive was designed for. A single Durable Object instance can coordinate multiple clients, and the Hibernation WebSocket API keeps connections alive while the object is evicted from memory ([Use WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)).
- **At 10–50 concurrent auctions**: 50 objects, 550 connections. Durable Objects are billed per request and per GB-s, not per object, so extra auctions cost almost nothing while idle.
- **Connection-model fit with serverless**: excellent from the client's point of view — the DO *is* stateful, so the serverless client needs no connection strategy at all. The cost is that the ordering authority moves out of Postgres.
- **Dominant failure mode**: **losing Postgres as the single ordering authority**, which is the whole of ADR 0002 and ADR 0006. Accepting a Bid because a Durable Object said so, then appending to Postgres asynchronously, means the durable record can lag the acknowledgement and two different answers can exist during a crash. You also inherit: DO placement is decided by the first `get()` unless you pass a `locationHint`, hints are best-effort and "not a guarantee" ([Data location](https://developers.cloudflare.com/durable-objects/reference/data-location/)); and **code updates disconnect all WebSockets** because deploying restarts every Durable Object ([Use WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)). Deploying during a Live Auction therefore ends every session.
- **Migration effort**: largest of the six. The command logic in `place-bid.ts`, `close-player.ts` and `live-command.ts` is reimplemented in a Worker; `src/domain/legal-completion.ts` and `tiered-completion.ts` must port to TypeScript-on-Workers (they already are TS, so this is mostly plumbing) or move to SQL; the entire realtime path (`grant.ts`, `notify-revision.ts`, `outbox.ts`, `distributor.ts`) is deleted and replaced; `use-live-sync.ts` is rewritten. Postgres stays for persistence and Reporting/Results, which means dual-write and reconciliation.
- **Monthly cost**: Workers Paid has a **$5/mo minimum** for the account and includes Durable Objects ([Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)). Durable Objects bill **$0.15 per million requests** (1M included) and **$12.50 per million GB-s** (400,000 GB-s included); **WebSocket messages are charged at a 1:20 ratio** ([Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)). Hibernation means "Billable Duration (GB-s) charges do not accrue during hibernation". One auction is therefore essentially the **$5/mo minimum**: Cloudflare's own hibernation example (100 objects × 100 hibernatable sockets, one message per minute, all month) totals **$20.65/mo**. SQLite-backed Durable Objects are available on the Workers Free plan with daily free-tier limits that reset at 00:00 UTC, subject to a 5 GB free storage cap ([Durable Objects limits](https://developers.cloudflare.com/durable-objects/platform/limits/), [do-plans-note](https://developers.cloudflare.com/durable-objects/platform/pricing/)). PartyKit is free to use against your own Cloudflare account and joined Cloudflare in April 2024; its hosted tier clears storage every 24 hours and allows 10 live projects ([PartyKit](https://www.partykit.io/)).
- **ADR verdict**: **breaks 0002 and 0006** (ordering and commit-before-acknowledge move to the actor), **breaks 0008** (brokered Supabase tokens replaced), keeps **0004** only if the Audit Entry still lands in Postgres. It **improves 0007**: Durable Object alarms are a native scheduled wake-up, which is exactly the five-second sweep that [the current flow](../live-auction-page-flow.md) records as unimplemented. Also **breaks 0005**.

### 5. Reactive/incremental sync layers (Zero, ElectricSQL, Convex, Liveblocks, Ably)

- **Change**: replace "broadcast a revision, pull a full authorised snapshot" with incremental sync. The command path can stay exactly as it is.
- **Bid latency expectation**: unchanged. **This is the key point.** These products are replacement *read* paths. None of them removes the row lock, the ~22 round trips, or the 7.7× finalize fan-out, so none of them fixes the measured 1,934 ms mean. They remove the 0.45 GiB/auction snapshot fan-out and make the UI correct without polling.
- **At 11 clients on one auction**: replaces `useLiveSync`'s 15-second/3-second polling and snapshot pulls with per-query incremental updates. Good fit for the read model.
- **At 10–50 concurrent auctions**: where these products earn their keep — read fan-out scales with writes instead of readers.
- **Connection-model fit with serverless**: Zero runs `zero-cache` as a separate long-lived service against a Postgres replica; Electric serves over HTTP with CDN caching; Convex is its own backend; Liveblocks and Ably are managed WebSocket edges. Supabase Realtime stays for commands either way.
- **Dominant failure mode**: a second source of truth for reads. `resolveLiveRole` and the per-caller filtering in `getLiveSnapshot` (rejected Bid details visible only to the Organizer and the submitting Representative, phone numbers excluded from the directory) must be re-expressed in the sync layer's permission model, or the layer leaks. With Zero that means mutators and query permissions in server code ([Zero](https://zero.rocicorp.dev/)); with Liveblocks it means room-level permissions.
- **Migration effort**: medium. `src/server/auction-query/live-snapshot.ts` and `live-players.ts` become sync queries; `use-live-sync.ts` becomes a subscription hook; `snapshot/route.ts` is deleted or demoted to a bootstrap read. `auction-command/*` is untouched. `notify-revision.ts`/`outbox.ts`/`distributor.ts` are replaced by the vendor's changefeed.
- **Monthly cost and region facts** (primary sources):
  - **Liveblocks** is a **non-starter** for this workload on the lower tiers: Free and Pro cap **simultaneous connections per room at 10**, i.e. below the 11 clients this Auction needs. Team (50) costs **$500/mo**, Enterprise (100) is custom. Free includes 3,000 realtime collaboration minutes/month; Pro is **$25/mo** including $30 of credits at **$0.002/minute** ([Liveblocks pricing](https://liveblocks.io/pricing)).
  - **Ably**: Free **200 concurrent connections**, 500 msg/s, 6M messages/month; Standard **$29/mo** with 10k concurrent connections and 2.5k msg/s. Metered at **$1.00 per million connection-minutes**, **$1.00 per million channel-minutes**, **$2.50 per million messages**. 11 clients × ~120 minutes ≈ 1,320 connection-minutes ≈ **$0.0013** per auction. Ably advertises "WebSocket edge infrastructure in 11+ regions and 700+ PoPs" and 6.5 ms message delivery latency ([Ably pricing](https://ably.com/pricing)). Ably does not publish a per-region list on the pricing page, so **Singapore presence is not verified**.
  - **Zero (Rocicorp)**: open source and self-hostable; managed Cloud Zero is **$30/mo** (Hobby: 10 GB, 3 shared vCPU) or **$300/mo** (Professional) or **$1000/mo+** BYOC ([Zero](https://zero.rocicorp.dev/)). Region is not stated on that page, so **Singapore availability is not verified**.
  - **Electric Cloud**: pay for writes and retention only — **$1 per 1M writes**, **$0.10 per GB-month**, reads/egress/fan-out free, with **+$2 per 1M writes** for the Postgres Sync service; usage under **$5/mo is waived**. Pro $249/mo, Scale $1,999/mo ([Electric pricing](https://electric-sql.com/pricing)).
  - **Convex** regions are `aws-us-east-1`, `aws-eu-west-1`, `aws-ap-southeast-2` (Sydney) and `aws-ca-central-1` ([Convex regions](https://docs.convex.dev/production/regions)). **There is no Singapore region**; Sydney is the nearest, which adds an inter-region hop to every write for a Singapore-registered client base.
- **ADR verdict**: satisfies **0002**, **0004**, **0006**, **0007** if the command path is untouched. **Breaks 0008** the moment it replaces Supabase Realtime with a vendor's socket and auth, and **breaks 0009** if the sync layer's mutators become a competing write path — the mitigation is to keep every fairness-affecting write on the Auction Command interface and use the sync layer for reads only.

### 6. Alternative Postgres providers

- **Neon**: `aws-ap-southeast-1` (Singapore) is a supported project region ([Neon regions](https://neon.com/docs/introduction/regions)). Pooling is PgBouncer in **transaction mode** with `max_client_conn = 10000`, `default_pool_size = 0.9 × max_connections` and `query_wait_timeout = 120` ([Neon connection pooling](https://neon.com/docs/connect/connection-pooling)). Free is 100 CU-hrs/month per project and 0.5 GB; Launch is **$0.106 per CU-hour** plus **$0.35 per GB-month** ([Neon pricing](https://neon.com/pricing)). The [serverless driver](https://neon.com/docs/serverless/serverless-driver) queries over HTTP or WebSockets, which is a genuine improvement over TCP-plus-pooler for a single round trip — but it cannot help while a command is 22 sequential statements. The difference from Supabase is a larger client ceiling (10,000 vs. the free plan's 200 pooler clients) and per-second compute billing; it is not a different answer to the row-lock question. Migration: `pool.ts`, `connection-string.ts`, and every `supabase/migrations/*` replayed into a new project; Supabase Realtime, Storage and Auth are left behind, which breaks ADR 0008 and ADR 0005's "Supabase ... for Realtime, and Team logo storage".
- **PlanetScale**: Postgres single-node starts at **$5/mo**, Metal at **$50/mo**; "Additional regions — Deploy in any AWS or GCP region with at least 3 availability zones" is listed under the **Enterprise** plan ([PlanetScale pricing](https://planetscale.com/pricing)). **Singapore availability for base-plan Postgres is not verified** from the primary page. PlanetScale also replaces Supabase Auth/Realtime/Storage wholesale, and its Postgres product does not remove the row lock, so it answers none of the measured problem. Not recommended for this workload.
- **ADR verdict**: any provider swap breaks **0005** and **0008** and does not fix the execution model. Only relevant if you need more than ~200 pooler clients without paying Supabase, which is an Option 1 scaling question, not an architecture question.

## Recommendation

**The stack is not too small. The execution model is wrong.** The proof is in the workload profile above: 0.09 commands per second, ~334 rows, a 67 KiB snapshot, and 1,245 seconds of lock wait in a 7,200-second auction, of which at most 283 seconds — and plausibly 0.6 seconds — is real statement execution. A database with 99% idle capacity is not under-scaled; it is being held open by the application.

**Phase 1 — this week. Configuration and protocol only. No new vendor, no new service.**

1. **Move to the shared transaction pooler on port 6543** and set an explicit small `max`. Supabase's own guidance for Vercel Functions is one connection per warm instance, prepared statements off, SSL required, client created at module scope ([connect guide](https://supabase.com/docs/guides/database/connecting-to-postgres)). This is a `src/server/database/pool.ts` change and an environment change. It removes the 4,900 `(EMAXCONNSESSION)` and 913 `Failed to get session` errors, which are a 15-backend session pool fighting node-postgres's default `max: 10` across many Lambda instances.
2. **Elect one finalizer.** 301 finalize commands for 39 Player Presentations is the single largest source of avoidable lock acquisitions (262 of them, 41% of all commands). ADR 0007 already says browser requests are only wake-ups; make the Organizer's client the designated waker, or have the caller's own command response schedule the due-only wake, and keep `finalizePresentation`'s idempotency as the correctness backstop.
3. **Stop sending Bids that cannot win.** 90 of 192 bids are rejected `stale_revision`. Have the client refuse to submit when `expectedRevision !== revision`, and suppress the custom-amount jump-bid path that the flow document already flags as diverging from the product specification. Removing these plus the surplus finalizers deletes **352 of 644 lock acquisitions (55%)** without touching a rule.
4. **Stop re-pulling the whole snapshot.** Return one authoritative shape with an ETag/revision key, drop the `players[]` + `openSales[]` + `teams[].players[]` triplication, and fold the four duplicated queries into one. This is the change that keeps egress honest: at today's shape the derived ceiling is ~11 auctions/month on the free plan.
5. **Rehearse it.** The existing `rehearsal:bid` script awaits bids in a loop and cannot rule out the reported failure, exactly as the earlier note says. It needs 11 concurrent sessions, snapshot polling, a full presentation lifecycle, and 39 presentations of finalize traffic before Phase 2 starts.

**Phase 2 — next two to four weeks. One round trip per command (Option 2).**

Turn each command into a single PostgreSQL function that locks, authorises, validates, writes the Bid, bumps the revision, writes the outbox event and Audit Entry, stores the command result, and returns the outcome. Keep `LiveCommandOutcome` and the Auction Command interface as the contract so `live-actions.ts` and the UI do not move. Keep the legal-completion engine single-sourced: either port it once into SQL and delete the TypeScript reachability engine, or replace the 200,000-node search with one set-based feasibility statement. Do not run two implementations — that is exactly the competing path ADR 0009 forbids. Expected effect: the row lock is held for server execution instead of for 22 await hops, which is the only way the measured 1,934 ms mean can plausibly become tens of milliseconds.

**Phase 3 — only when the beta needs it. Trigger conditions decided in advance.**

- **> 1 concurrent Live Auction or any commercial use**: upgrade Supabase to Pro (**$25/mo**, removes pausing, 8 GB disk, 500 Realtime connections included) and Vercel to Pro (**$20/mo**; Hobby is documented as non-commercial — "Our Hobby plan is for personal, non-commercial use"). This is the point at which ADR 0005 must be superseded, because ADR 0005 itself already caps the beta at one Live Auction, 16 Teams, 40 tabs, and no commercial use.
- **> ~2 concurrent auctions, or command latency that Phase 1–2 cannot hold under 250 ms**: take Option 3. A `shared-cpu-1x`/`shared-cpu-2x` Fly Machine in `sin` (**$1.94–$3.89/mo**, volumes $0.15/GB/mo, AP egress $0.04/GB) plus Supabase Pro gives a warm `pg.Pool`, a direct connection, and no pooler in the command path. Railway `asia-southeast1` (Singapore, $5/mo + usage) and Render Singapore ($7–$25/mo) are equivalent. Keep Supabase Realtime and ADR 0008 at first; add an in-process socket only if Realtime's 2,500 msg/s Pro ceiling or its connect behaviour becomes the constraint, and write a superseding ADR when you do.
- **> 20 concurrent auctions, or a hard requirement that a browser refresh never sees a stale Roster**: consider Option 4 (Durable Object per Auction, $5/mo minimum, alarms replacing the missing sweep) or Option 5 (Electric or Ably for reads). Both require superseding ADR 0008, and Option 4 additionally requires superseding 0002 and 0006 — accepting that Postgres stops being the thing that decides who won. Do not do this while a correctness-critical ADR says otherwise.

**What not to do.** Do not move to Neon, PlanetScale, Convex or Zero hoping for latency relief. None of them removes the row lock, the 22 round trips, the 7.7× finalize fan-out, or the stale-revision storm. Liveblocks' lower tiers cannot even hold 11 simultaneous connections in a room. Convex has no Singapore region. These are answers to the read-fan-out question, which is not the question the measurements are asking.

## What I could not verify

- **Hetzner Cloud prices.** The Singapore (SIN1) location is confirmed, but the product tables render monthly/hourly figures client-side and no figure appeared in the fetched page, so none is quoted.
- **Cloudflare Durable Objects free-tier daily allotments.** The specific daily numbers live in a docs partial that could not be rendered. Confirmed instead: SQLite-backed Durable Objects are available on the Workers Free plan; exceeding any free-tier limit fails that operation for the rest of the UTC day; free storage is capped at 5 GB ([limits](https://developers.cloudflare.com/durable-objects/platform/limits/)); Workers Paid carries a $5/mo account minimum.
- **PartyKit's current commercial terms.** `partykit.io/pricing` returns 404; the marketing page's pricing section is the source quoted.
- **Singapore presence for PlanetScale base-plan Postgres, Ably, and Zero Cloud.** Not stated on the pages that own those claims.
- **Supabase's IPv4 add-on price**, which matters if a container connects directly over IPv4; it is not on `supabase.com/pricing`.
- **Whether this project's Vercel deployment has Fluid compute enabled.** Vercel requires it for WebSockets and it is the default only for projects created on or after 2025-04-23. Note also the correction this implies for the earlier note: Vercel Functions *can* now serve WebSockets, in public beta on all plans — but a connection is closed at the Function's maximum duration, which is 300 s on Hobby and 800 s on Pro, so a two-hour auction session still cannot live in a Vercel Function socket ([WebSockets](https://vercel.com/docs/functions/websockets), [limits](https://vercel.com/docs/functions/limitations)).
- **Whether the 1,934 ms lock-wait statistic includes time spent waiting for a Supavisor backend**, rather than time waiting on the row lock. `pg_stat_statements` mean execution time includes lock acquisition, and the pooler sits in front of the database; separation would need `pg_locks` samples or pooler metrics. The argument in this note holds under either reading, because the statement-work ceiling of 283 s is 4.4× below the measured 1,245 s of lock wait.
